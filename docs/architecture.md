# How it works

```
browser / TV / phone (public/)  <->  server.js  <->  src/meta.js       catalog and artwork metadata, disk-cached
                                                <->  src/sources.js    torrent search providers, ranked
                                                <->  src/release.js    release-name parsing: title, episode, pack, file choice
                                                <->  src/tracker.js    live seeder counts from UDP trackers
                                                <->  src/ids.js        anime id mapping (AniList to Kitsu, AniDB, IMDb, TVDB) and episode numbering
                                                <->  src/engine.js     torrent client, library, storage cap
                                                <->  src/local.js      your own media folders
                                                <->  src/transcode.js  stream probe, on-demand HLS, hardware encoder
                                                <->  src/subs.js       subtitle providers
                                                <->  src/skips.js      intro, recap and ending markers
                                                <->  src/state.js      profiles, progress, My List, settings
                                                <->  src/lock.js       profile PINs: hashing, session tokens, throttling
                                                <->  src/images.js     poster proxy with disk cache
```

## Play flow

1. `POST /api/play` picks, in order: a matching local file, an existing download of the same episode, the best-ranked torrent not on the client's `exclude` list.
2. The client polls status while `/api/info` probes the file with ffmpeg. If nothing arrives for 25 s (40 s to find the torrent), the client excludes that source and the server picks the next, up to five times. Stalled torrents with no data are removed.
   The probe first reads the file's first kilobyte and refuses playlists and session files (`#EXTM3U`, `ffconcat`, `<MPD`, XML, SDP) named like a video. The bundled ffmpeg already rejects most of them, but it accepts an SDP file as an RTP session and would open network sockets for it. ffmpeg inputs that arrive over a pipe are limited to the `pipe` protocol.
3. `/raw/:id/:file` serves bytes with range support. MP4/WebM with H.264 and AAC plays directly; anything else goes through HLS (6 s segments encoded on request by ffmpeg, the next two warmed). The encoder is chosen at start (NVENC, VideoToolbox, VAAPI, else x264) by test-encoding a frame.
4. Once the file is probed the player asks `/api/skips/:id` for the intro, recap and ending. Per marker the first source wins: the file's own chapters (titles like Opening, OP, Credits), then AniSkip for anime (by MAL id) and IntroDB for series (by IMDb id). AniSkip times are used only when the recorded length is within 12 s of the file's, and no marker is kept that cannot be right (an intro in the second half, an ending in the first). Results are cached for 6 hours, nothing found for 30 minutes. The player shows Skip intro or Skip recap while a marked part plays, and the Up next card at the start of the ending (28 s before the end when there is no marker).
5. Progress is saved per profile every few seconds. Halfway through an episode the next one starts downloading. The oldest unwatched downloads are removed when the storage limit is reached.

## Choosing a source

`src/sources.js` ranks candidates by resolution, seeders, codec, language, and whether the bitrate fits the line's measured speed (`src/speed.js`) and the viewer's Download size mode. The best fifteen are first asked of the UDP trackers (`src/tracker.js`), because a seeder count a source lists can be days old; a live count is used when two trackers agree. On play the top few start together for a few seconds and the fastest real downloader wins; the others are removed. Magnets carry a fixed tracker list plus a community list of healthy trackers refreshed twice a day.

`src/release.js` is the single place that reads torrent and file names. It answers whether a release is the requested title (and not a longer title that contains it), whether it is the requested episode under any of the numberings fansubs use (season and episode, absolute, from 1), whether it is a pack, and which file of a pack to open. Names are parsed once and cached.

Lookups run in two tiers and return within about 300 ms of the primary source answering; sources that answer later top up the cached list (kept 90 minutes, "nothing found" five minutes), and the next episode's list is fetched when playback starts. The first asks sources keyed by id: Torrentio by IMDb id for movies and series, and for anime by Kitsu id plus AnimeTosho by AniDB episode id. `src/ids.js` keeps the Fribb anime id list on disk (refreshed daily) and fetches a show's ani.zip episode table once, which gives each AniList episode its Kitsu and AniDB ids and the TVDB and absolute numbers releases use; those numbers also go to the engine so a multi-file pack opens the right episode. Rows an id vouches for still pass a numbering and year check. Only when the first tier returns fewer than three seeded releases does the second tier search by name: YTS, TPB and Knaben for movies, TPB and Knaben for the episode, the season and the complete series, and Nyaa and the AnimeTosho show listing for anime (plus sukebei for Hentai-marked titles when the adult filter is off).

## Streaming to every device

Browsers get the file directly when it is a real mp4/webm with H.264/VP9/AV1 video and AAC/MP3/Opus audio. Everything else is transcoded to H.264 High 4.1 (no B-frames) and AAC stereo HLS that Safari's native player accepts; if native HLS fails hls.js is tried, and the other way round.

## Reliability and caching

Outbound requests go through `src/http.js`: retries with jittered backoff, a per-provider rate limit, a circuit breaker, and merging of identical requests in flight. Catalog data lives in a stale-while-revalidate cache (`src/meta.js`): served at once, refreshed in the background, kept up to a week if the provider is down. Torrent searches are cached for 90 minutes, subtitle lists for 6 hours; subtitle files, posters and translations are cached on disk. Nothing built while a source failed is kept as if it were whole: a failed search is an error rather than "no results", a list or value assembled with something missing (subtitles without the slower provider, artwork or episode names that did not load, sources without the one that errored) is kept for a minute or two, and the browser is not told to keep an empty list.

## Subtitles

**Built-in tracks.** `GET /api/sub/embedded/:hash/:file/:track` extracts a track with ffmpeg, reading the file from disk rather than the torrent stream (a seek into missing pieces would wait forever). While downloading, only the unbroken start counts (`readablePrefix` in `src/engine.js`); `x-covered` says how many seconds the answer reaches, and `/api/status` reports the same prefix as `readable`, so the menu enables a track only when the server can serve it. Finished results are kept in `data/subs`.

**Files in the torrent, and beside local files.** `src/sidecar.js` picks the `.srt`, `.ass`, `.ssa` and `.vtt` files of the torrent (or, for a local video, of its folder and `Subs` folder) that belong to the watched file (same name, a folder named for the episode, or any file when the torrent has one video) and guesses the language from the name. `/api/info` lists them, `/api/sub/file/:hash/:idx` reads one through the torrent (its few pieces jump the queue) and serves WebVTT. They match the release's own timing, so Auto sync leaves them alone like built-in tracks.

**Placement.** Subtitle files converted from ASS carry override blocks in their text. `srtToVtt` in `src/subs.js` turns alignment (`{\an1}` to `{\an9}`, and the older `{\a1}` to `{\a11}`) into the cue's WebVTT `line` and `align` settings and `{\i1}`/`{\i0}` into `<i>`, and drops the rest (`{\pos}`, `{\fad}`, colours, fonts, `<font>`). Settings ride on the timing line, so translation and sync keep them. Built-in and uploaded ASS go through ffmpeg's SRT writer because its WebVTT writer drops alignment; built-in WebVTT and mov_text tracks carry none. The player draws three places (top, middle, bottom) and a cue that asks for a side hangs from a 5% margin; the top and bottom places move clear of the controls while they show. A place holds one side at a time: when cues in the same place disagree, the last decides.

**Download limit.** `dl.opensubtitles.org` answers 404 once an IP's anonymous download quota is used up. `fetchSubtitle` then refuses its files for an hour with a 429 (so no more requests count toward a firewall ban), the list flags them `limited`, and the player disables them and skips them when picking automatically.

**Profile account.** Settings and the player's limit message can connect an OpenSubtitles account to the profile in use (`src/osaccount.js`, saved by profile id in `data/opensubtitles.json`, never sent back to the browser, removed with the profile). `fetchSubtitle` and `listSubtitles` take the profile, so one profile's account is never used for another's downloads; the profile rides along on the player's request and on the server's own inner subtitle requests. Once the anonymous quota is hit, downloads go through the legacy XML-RPC `DownloadSubtitles` with that login, using the file id from the download link; the account's own limit (`407`) pauses it for a day, and files are flagged `limited` only when neither route works. This route only works for VIP members of opensubtitles.org: any other account gets a placeholder file (one four-hour cue selling VIP) back with `200 OK`. `fetchSubtitle` recognises it, never caches it, sets the account aside for a day (`vipOnly` in `GET /api/opensubtitles`) and answers 429, and Settings and the player's message say why.

**Sync.** `src/sync.js` (in a worker thread) reads audio windows from whatever parts of the file are on disk (`engine.readableRuns`, turned into seconds and trimmed at the ends because bytes map to time only roughly), the one around the playhead first and then the farthest ones, turns them into a speech-strength signal and cross-correlates it with the cue times (FFT). Windows that agree give a constant offset, ones that move steadily give drift, and groups give a splice. `public/js/syncmap.js` applies the result; while playing, the player asks `/api/sub/sync?at=` for a fresh window about every 75 s. The player keeps the result and the manual timing per episode in the title's browser storage (`fix`), tied to the release it was measured on, so continuing to watch shows it at once while the server measures again in the background. When the video has a text track built in, `trackReference` in `server.js` extracts its first minutes from disk (as the built-in subtitle route does) and the worker measures the subtitle's cue times against that track too: the track is the audio's own timing in text, so a lock (peak 0.55 or more, where another episode's cues stay under 0.45) settles offset and frame rate without reading audio, and a track that covers minutes without a lock stops a lone weak audio window from being trusted. Each pass keeps the windows measured before (`evidence`) and reads only stretches not yet seen, so the answer improves as the file arrives: the server runs another pass after 40 s more can be read, and the player asks again every minute while the file is partial. Window length and count were picked with `npm run bench -- sync` ([results](benchmarks.md#auto-sync-sync)).

**Translation.** `src/translate.js` translates an English subtitle with the Bergamot engine and its public models (MPL-2.0, npm `@browsermt/bergamot-translator`) in a pool of worker threads. Models are checked against their SHA-256 and cached, results are cached per subtitle and language, and the result is served as an ordinary WebVTT file at `/api/sub/translate?src=&to=`. Leaving a translation cancels the work.

**Better translation (optional).** `src/translate-hq.js` (setting `bestTranslation`) installs NLLB-200 distilled 600M through transformers.js into `data/translate/hq` on demand and runs it in child processes, on the GPU through WebGPU when a fast one is found, else on the CPU. `translateBetter` serves the standard translation at once and improves it from the playhead; improved lines are saved so a restart resumes. The NLLB-200 weights are licensed CC BY-NC 4.0, so this option is for personal use.

## Audio

ffmpeg's report lists audio tracks with language, title and default flag. The player starts on the track in the title's `originalLanguage` (from the production country, or Japanese for anime), skipping tracks titled as a dub or commentary, and falls back to the file's default flag. A track other than the file's own default always goes through HLS.

## Watch party

`src/party.js` joins a party by code. The code (80 random bits, plus the optional password when there is one) goes through scrypt into a 20-byte torrent id and a 32-byte key. The server adds that id as a magnet-only torrent on its own small torrent client (the public WebRTC trackers and DHT find the other members, WebRTC gets through routers), and talks over a BitTorrent extension message (`dodobox_party`). Every message is AES-256-GCM sealed with the key, numbered per sender and timestamped, deduplicated, and passed on to the other neighbours, so members who cannot reach each other directly are bridged by one who can reach both. Messages are `hi` (presence), `st` (what is playing), `ld` (changed title), `pl`, `pa`, `sk` (play, pause, seek) and `tk` (heartbeat from whoever acted last) `rx` (a reaction to a message, one of six emoji, sent again to take it back) and `ch` (chat text, up to 500 characters; the last 100 are kept in memory for the page and are not sent to members who join later). Titles and versions from other members are validated before they reach the page; the version is only an info hash, and `/api/play` plays it only when this server's own search lists it, otherwise the best listed version, so a member can never make another member's server fetch a torrent of their choosing. Each sender has a small message budget (a burst, refilled over time) and member colours must be hex. The API refuses non-GET requests from another site (`Sec-Fetch-Site`, or `Origin` when absent) and any `Host` that is not an address, `localhost`, a single-word name or a `.local`/`.lan` style name unless it is in `ALLOWED_HOSTS` (DNS rebinding; forwarded headers are not trusted because a page can set them).

The page (`public/js/party.js`) reads `/api/party/events` (server-sent events) and posts `/api/party/send`. The player reports its own play, pause and seek, and ignores the echo of what it just did on someone else's say. A party can start empty (a lobby): the first player to start fills it with `ld`/`st`, and when the next episode of the same title is loaded by someone, players already on that title follow. A joiner starts on the party's version and position.

## Interface

Vanilla ES modules, no build step. `nav.js` handles arrow-key navigation and the Back key for TV remotes. The player draws its own controls and subtitles and supports Cast, AirPlay, Media Session, Picture-in-Picture and wake lock. `sw.js` caches the shell, catalog data and posters for offline browsing; bump its `VERSION` when a shell file changes. Per-title player options live in `localStorage` under `title:<profile>:<type>:<id>`.

## Desktop app

`desktop/main.js` is a tray-only Electron app: it sets `DATA_DIR` to the user data folder, starts `server.js` in the same process (on a free port if 3000 is taken) and offers a tray menu. It has no window; the page opens in the system browser. Starting it again opens the page, or quits with `--quit`. Packaged with electron-builder without an asar archive, so the worker and WebAssembly files stay plain files; `desktop/prune.cjs` drops other platforms' ffprobe and native prebuilds and ad-hoc signs the macOS app. Electron emits `ready` only after the entry module finishes evaluating, so the entry must not await it at the top level. Updates: the app uses `electron-updater` against the releases page. It never downloads on its own: `autoDownload` is off and the user is asked first. Only the Windows installer and the Linux AppImage can replace themselves, so the workflow uploads `latest.yml` and `latest-linux.yml` next to the installers (the macOS file is skipped: unsigned builds cannot self-update and the two architectures would overwrite each other). Server runs (Docker, npm) and the desktop builds that cannot replace themselves (macOS, portable, `.deb`) use `src/update.js`, which compares the latest release with `package.json` and logs a hint; the desktop app turns it into a question that opens the download page. On those builds `electron-updater` is never started, since it would look for `latest-mac.yml` and similar files that are not published. The release workflow builds each platform on its own runner (the bundled ffmpeg is the runner's) and attaches the installers to the release.

## Data versions

Everything Dodobox keeps is versioned, so a release can change how it is stored and upgrade existing installs by itself.

- **Server:** `data/schema.json` holds the data version: how many migrations the folder has been through. Each migration is a file in `src/migrations` named for the version it produces (`002-...js`), listed in order in `src/migrations/index.js`; a test checks the files and the list agree. `src/data.js` runs the ones a folder has not seen at startup, before any module reads its files, and every module that loads from the data folder imports it first. An install that skipped releases runs each missing step in turn. A folder with files but no version file is version 0, so `001-baseline` is what versions existing installs; an empty folder is stamped current. Before the first step the JSON files are copied to `data/backups` (the newest three are kept, caches excluded); if a step throws, the files and version are put back and Dodobox stops with a message. A data folder from a newer Dodobox is refused, so an older version never edits it. Steps get `read`, `write` (atomic) and `drop` (for caches) and must cope with missing files.
- **Browser:** `STORE_STEPS` in `public/js/util.js` does the same for `localStorage`, tracked under the `dbx-schema` key.

To change a stored shape: add the next numbered file and list it, write a test with the old shape, and leave older files as they are.

## Tests

`npm test` runs unit tests, an offline end-to-end test (local seeder, download, probe, HLS, subtitles; needs `ffmpeg` on the path), library, profile API, HTTP client, sync and translation tests, and static checks of the frontend. `npm run lint` runs ESLint.
- **Logging:** `src/log.js` is imported first by `server.js`. `log.debug|info|warn|error(tag, message, fields)` and any `console.*` go to `data/logs/dodobox.log` (rotated at 8 MB); info and above also print. The page reports its errors, player events and failed requests to `POST /api/log` (`public/js/report.js`). Request bodies are logged field by field with `pin`, `current`, `password`, `code`, `token` and `text` masked. A failure that is handled by carrying on still logs at debug (`swallow` in `server.js`), so no `catch {}` hides what went wrong.
